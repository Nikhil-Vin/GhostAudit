# GhostAudit — Deletion-Audit Agent

A deterministic Python pipeline that audits whether a user's personal data was really deleted. It resolves every
identifier a person has ever used, reconstructs the state of each related resource at `audit_at` from the supplied
evidence, applies the deletion policy, and emits an ordered, evidence-cited remediation plan.

It makes no model calls, needs no API keys, and uses no network access. Every run on the same inputs produces
byte-identical output.

The full 518-case run (`output.csv`) has 346 `INCOMPLETE`, 162 `COMPLETE` and 10 `NOT_APPLICABLE` rows.

## Quick start

Requirements: Python 3.10+. The core uses only the standard library. PDF evidence is read with `pdftotext`
(poppler-utils); if it is missing the code falls back to `pypdf` (`pip install pypdf`).

```bash
# from the repository root
python3 code/main.py                 # reads dataset/, writes ./output.csv (518 rows)
python3 code/evaluation/main.py      # re-scores samples, runs custom cases, rewrites evaluation/*.md
```

Package the submission archive (excludes `dataset/` and caches):

```bash
zip -r code.zip code -x "*/__pycache__/*" "*.pyc" "code/evaluation/_sample_predictions.csv"
```

## Architecture

```
deletion_requests.csv ──► intent_classifier ──► NOT_APPLICABLE, []        (non-deletion request)
                              │ deletion
                              ▼
user_identities.csv ┐
user_audit_log.csv  ┴─► identity_resolver ──► alias graph (emails, hashes, phones, user ids)
                              │
evidence/* + evidence_files.csv ─► evidence_indexer ──► uniform facts (resource, state, time, file_id)
system_activity.csv ──────────────┤
deletion_rules.csv ───────────────┤
                              ▼
                           auditor ──► status + findings / remediation / verification
                              ▼
                            sorter ──► validated, ordered, numbered steps ──► output.csv
```

| Module | Responsibility |
|---|---|
| `intent_classifier.py` | Decides whether `request_text` authorizes deletion. Preservation phrases ("I am not asking for deletion", "leave the account active") are checked first, then explicit delete cues (en, fr, es, pt, de, ja, ko, ar), then access / export / correction topics. |
| `identity_resolver.py` | Builds the alias graph from the current snapshot and the audit log; resolves the request email as of `requested_at`; excludes identifiers shared between users to avoid false matches. |
| `evidence_indexer.py` | Parses SQLite dumps (primary and replica tables), JSON bundles, text handovers, PDFs and logs in five dialects (key=value, JSON lines, bracketed, pipe-delimited, syslog), correlating lines by trace id. |
| `auditor.py` | Links resources to the subject, classifies each resource's latest state inside the audit window, applies the policy and builds the steps. |
| `sorter.py` | Validates phase / operation / state combinations, de-duplicates, sorts and numbers steps. |

## Decision logic

1. **Authorization.** Only requests that actually ask for deletion are audited; everything else is `NOT_APPLICABLE` with `[]`.
2. **Identity.** The request email may be current or historical. Hashes, phones and user ids found in evidence link back to the same person.
3. **Time.** Resource identifiers are static, so linking may use any evidence from `requested_at` onward. State is judged only from
   read-backs between `requested_at` and `audit_at`; the latest observation wins. Evidence captured after `audit_at` is never used or cited.
4. **Claims are not proof.** `reported_status` and activity `reported_result` are never accepted as the state of a resource.
5. **Policy.** Each linked resource is mapped to its `deletion_rules.csv` treatment: delete, redact, anonymize, retain, or preserve a tombstone.
6. **Plan.** A case is `COMPLETE` only when every copy has its required treatment, required retained records exist, and no active
   flow or restore path can recreate data. Otherwise it is `INCOMPLETE`, with data flows disabled and restores blocked before
   dependent records are changed.

## Output contract

`output.csv` has the columns `case_id,deletion_status,steps_json`, one row per case, sorted by case id. Each step has exactly
`step_no, phase, system_id, resource_id, operation, state, evidence_id`. Steps are ordered by phase, then operation order,
then `system_id`, then `resource_id`, and numbered from 1. Findings and `COMPLETE` verifications cite a participant-visible
`file_id`; remediation and post-remediation verification steps use an empty `evidence_id`.

## Evaluation

## Limitations

- Resources that carry no identifier and are not tied to the person by any visible link (for example some anonymized analytics
  records, or retained audit records never mentioned in evidence) are not guessed, so their verification steps can be missing.
- When several candidates share the same reported time and none names an identifier, the link is ambiguous and skipped.
- Screenshots are not OCR-parsed, and legal-hold records are not modelled.
- Two evaluation cases (`case_61`, `case_63`) resolve to `COMPLETE` with no steps because no resource could be linked.
